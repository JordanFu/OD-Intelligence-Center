# 2026-07-04｜专题三：岗位、族群、序列的持续建设

## 1. 今日一句话专题判断

岗位体系继续“双向分化”：多数业务/应用岗位变宽为端到端责任包，AI agent operations、agentic systems、FDE、AI safety、evaluation、AI infra 等领域变深并出现薪酬化 JD 证据；但新增岗位/族群/序列前，仍要先判断它是稳定责任包，还是涨薪、保留、项目激励和市场溢价诉求。

## 3. 今日核心判断

1. **岗位体系主线仍是“双向分化”。可信度：高。** 应用/业务岗位变宽，专家/治理岗位变深；今天新增的 Redox/Postman/Figure JD 强化了 agent operations 与 agentic systems 两端。
2. **agent operations / governance 已进入岗位族候选，但不应立刻变成全公司序列。可信度：中高。** Redox JD 已经写出标准、阈值、合规、人机交接和业务指标，但仍缺多公司统一职业阶梯。
3. **FDE / Frontier 类责任包继续加厚。可信度：高。** Microsoft Frontier Company 与 AWS FDE 共同说明，客户现场工程、行业知识、AI engineering、change management 和结果责任正在组织化。
4. **取消 title 不等于取消岗位架构。可信度：高。** Cars24 可以取消外显头衔和层级政策，但薪酬、晋升、招聘定级、合规职务和职业成长仍需要内部架构。
5. **新增岗位/序列请求必须先拆真实诉求。可信度：高。** 如果诉求是市场加价、关键人保留、项目战功或短期稀缺，优先用技能标签、稀缺系数、项目奖金、专项津贴、薪酬带宽或股权刷新。

## 4. 重点案例事实还原

### 案例 A：AI Agent Operations / Governance JD

**背景。** 企业开始把 AI agents 放入客户成功、支持、产品和运营流程，传统岗位无法覆盖 prompt 质量、准确率阈值、人机交接、合规和持续监控。

**时间线。** 2026 年近窗招聘中，Redox、Postman、Figure AI 均出现 AI agent 相关原始 JD。

**动作。** Redox 将 AI agent manager 放在 customer success operations 中，要求审计现有 agents、制定构建/测试/维护标准、监控 CSAT、deflection、resolution accuracy，并处理 HIPAA 合规和人机交接。Postman 则把 AI Agent Development Lead 定义为跨职能部署和安全对齐岗位。Figure AI 聚焦 agentic systems、评估和可靠性。

**机制。** 这些岗位都不是简单“会用 AI”，而是把 agent 的质量、可靠性、评估、安全、合规、业务结果和跨团队协作写进责任包。

**结果。** 原始 JD 已公开薪酬区间，说明市场开始给这些责任包定价。

**争议和阻碍。** 单个 JD 不能证明成熟序列；不同公司岗位名称、归属、层级和晋升路径仍不一致。

**可借鉴点。** 企业可先设“agent owner / agent operations owner / evaluation owner”角色标签，绑定具体流程和指标。

**不可照搬点。** 不要把所有客服运营、产品经理或工程经理都改名为 AI Agent Manager；先看是否真实承担准确率、升级、人机交接、合规和业务结果。

### 案例 B：Microsoft Frontier Company

**背景。** 企业客户从 AI 实验转向 measurable business outcomes 和 ROI，需要行业知识、change management、continuous improvement 与 enterprise-grade AI engineering。

**时间线。** Microsoft 2026-07-02 官方发布 Microsoft Frontier Company。

**动作。** Microsoft 投入 $2.5B，嵌入 6,000 名行业和工程专家到客户侧，共同设计、创新、部署并持续改进 AI systems；官方称该组织超越传统 FDE，强调 outcome-driven engineering。

**机制。** Frontier 责任包包含客户 proprietary data、expertise、workflows、decision-making processes 的保护与放大，模型多样性、治理、安全、FinOps 和持续改进循环。

**结果。** 官方列出 LSEG、Land O'Lakes、Unilever、Novo Nordisk 等早期客户案例，但公开指标仍需要进一步验证。

**争议和阻碍。** 与咨询、系统集成、专业服务、产品工程和客户成功边界可能重叠；失败责任和结果归因仍需明确。

**可借鉴点。** 内部岗位族设计可以把“客户现场工程 + 变革管理 + 业务结果 + 知识保护”作为一个责任包候选。

**不可照搬点。** 普通企业不应按大厂规模直接设 Frontier 大组织；应先从关键客户、关键流程和关键行业场景试跑。

## 7. 对我们行动的启发

**什么时候新建岗位。** 长期稳定、多业务重复、端到端责任清楚、有质量/风险/决策问责、有任职资格和绩效指标、有外部薪酬对标时，才新建岗位。

**什么时候新建族群。** 多个相邻岗位共享能力模型、成长路径、评价标准和市场供给逻辑，例如 FDE / Frontier、agent operations、agentic systems 可作为候选。

**什么时候新建序列。** 只有当职业发展、晋升证据、薪酬带宽、专家深度与管理路径都独立时才建；序列是最高门槛。

**什么时候只用技能标签。** AI fluency、提示词、AI 输出校验、自动化意识、基础 agent 使用等跨岗位、变化快、不能独立问责的能力。

**什么时候用市场稀缺系数。** 原岗位不变，但 AI safety、model evaluation、AI infra、industry AI architecture、agent reliability 等能力外部市场明显加价。

**什么时候用项目激励。** 短期攻坚、关键客户部署、核心流程 agent 化、风险治理专项，不构成长期岗位。

**什么时候用专项津贴/临时补贴。** 临时值班、过渡期额外责任、阶段性风险治理、短期能力缺口。

**什么时候用薪酬带宽/LTI。** 长期市场价系统性上移，原带宽无法招聘或保留关键专家。

**什么时候坚决不新增序列。** 只是新工具、新 title、单个关键人涨薪、短期项目、单团队需求、缺评价标准、缺晋升路径、缺薪酬对标、业务想争预算或晋升名额。

## 8. 待验证清单与下一步搜索路径

1. Microsoft Frontier Company 是否公开具体岗位族、职级、绩效指标、晋升路径和客户 outcome 数据。
2. Redox/Postman/Figure 类岗位是否在更多公司复现，形成稳定命名、薪酬带宽和职业阶梯。
3. Workday ASOR 是否出现客户级 agent owner / agent governance job family 样本。
4. Cars24 Flatland 是否公开薪酬、晋升、招聘定级和管理责任替代机制。
5. 国内企业是否公开 AI 序列、AI 职级、AI 津贴、AI 项目奖金或关键人才保留制度。
6. 技能薪酬是否有 sunset、audit、pay equity 和市场稀缺系数机制。
