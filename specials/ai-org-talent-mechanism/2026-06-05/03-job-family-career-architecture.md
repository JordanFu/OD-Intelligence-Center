# 2026-06-05｜专题三：岗位、族群、序列的持续建设

## 1. 今日一句话专题判断

今天岗位/族群/序列最值得关注的新变化是：组织开始用 **role flow + capability package + pay logic** 来重写岗位，而不是继续靠静态 title 目录解释工作变化；很多新角色未必该直接做成新序列，但 `FDE / technical architect / verifier / agentic orchestration` 已经显示出稳定化趋势。

## 2. 今日新增事实：只写可追溯事实，注明来源

1. **OpenAI Deployment Company（2026-05-11）**明确使用 `Forward Deployed Engineers` 和 `Deployment Specialists` 两类角色，并说明 FDE 会与 business leaders、operators、frontline teams 一起 redesign infrastructure、critical workflows 和 production systems。  
   - 来源：OpenAI  
   - https://openai.com/index/openai-launches-the-deployment-company/
2. **Anthropic Claude Partner Network（2026-03-12）**公开 `Applied AI engineers`、`technical architects`、`Claude Certified Architect` 和 `Code Modernization starter kit`。  
   - 来源：Anthropic  
   - https://www.anthropic.com/news/claude-partner-network
3. **MiniMax Agent Team（2026-05-27）**将多 Agent 协作的基础角色明确为 Leader、Worker、Verifier，并进一步拆出 Tester、Reviewer 等专业化验证角色。  
   - 来源：MiniMax  
   - https://www.minimax.io/blog/minimax-agent-team-long-running-1779893953
4. **Mistral × Emmi AI（2026-05-23）**披露，Emmi 的 30+ researchers and engineers 将并入 Mistral 的 Science 和 Applied AI teams，目标是构建 best-in-class agents for engineers。  
   - 来源：Mistral  
   - https://mistral.ai/news/accelerate-ai-native-industry/
5. **McKinsey（2026-04-06）**把一个关键问题写得非常明确：哪些能力应该由员工建设，哪些应该训练 agents 去部署。  
   - 来源：McKinsey  
   - https://www.mckinsey.com/capabilities/mckinsey-technology/our-insights/designing-an-end-to-end-technology-workforce-for-the-ai-first-era
6. **EY Future of Pay 2026（PDF）**指出，45%-50% 的组织已走向 skills-based pay；同时将 skill taxonomies embed 进 job architecture，用 pay bands + skill tiers + proficiency levels 承接，并把 skill premium 的 recalibration 提高到半年或季度。  
   - 来源：EY  
   - https://www.ey.com/content/dam/ey-unified-site/ey-com/en-in/newsroom/2026/02/ey-future-of-pay-report-2026.pdf

## 3. 今日核心判断：3-5 条，每条注明可信度、证据基础、为什么重要

1. **很多“新岗位”本质上是稳定的新角色包，而不是一时 buzzword。可信度：高。**  
   - 证据基础：OpenAI 的 FDE / Deployment Specialists、Anthropic 的 Applied AI engineers / technical architects、MiniMax 的 verifier / reviewer、Mistral 的 Science + Applied AI team 组合。  
   - 为什么重要：这意味着企业不能再把这些角色都当成临时项目职责。
2. **岗位体系正在从 title 转向“角色流 + 能力包 + 验证责任”。可信度：高。**  
   - 证据基础：MiniMax 的 role flow 明确；OpenAI 与 Anthropic 都用跨职能、跨环节角色来定义交付。  
   - 为什么重要：未来的岗位设计，更像定义 who owns which stage of the loop，而不是给每个人一个静态名字。
3. **不是所有变化都应该做成新序列；很多变化更适合先用 skills tag、稀缺溢价或项目角色承接。可信度：中高。**  
   - 证据基础：EY 明确把 skills-based pay、pay bands、skill tiers、quarterly/biannual recalibration 做成核心机制。  
   - 为什么重要：如果把所有新能力都做成新序列，组织很快会出现 title inflation 和 pay logic 失控。
4. **真正值得新建族群/序列的，是那些同时满足长期性、跨团队可迁移性、可评价性和高责任边界的角色。可信度：中高。**  
   - 证据基础：OpenAI 的 FDE、Anthropic 的 technical architect、Mistral 的 industry engineering roles 已明显超出一次性项目。  
   - 为什么重要：这给“什么时候坚决不新增序列、什么时候必须承认新角色”的判断提供了门槛。  

## 4. 重点案例事实还原：从 FDE 到 Technical Architect，AI 时代岗位包如何形成

- 背景：过去很多企业会先问“要不要设 AI 岗位”；今天更好的问题是：哪些角色已经稳定出现，并且承接了新的责任链。  
- 时间线：  
  - 2026-03-12：Anthropic 发布 Claude Partner Network。  
  - 2026-05-11：OpenAI 发布 Deployment Company。  
  - 2026-05-23：Mistral 宣布并购 Emmi AI。  
  - 2026-05-27：MiniMax 公开 role flow。  
- 原组织形态：  
  - 产品、实施、架构、研发和客户成功之间边界较硬；  
  - 许多 AI 落地任务被塞进“创新项目”或“架构支持”模糊容器；  
  - title 和 pay logic 跟不上新责任。  
- 新组织形态：  
  - `FDE / Deployment Specialist`：把模型接进核心流程、数据、controls、business process。  
  - `Applied AI engineer / Technical architect`：承接 live customer deal、复杂实施、技术方案界定。  
  - `Leader / Worker / Verifier / Tester / Reviewer`：承接 task decomposition、execution、evidence-based verification、risk review。  
  - `Science + Applied AI + industry experts`：承接高 stakes 行业能力和 agents for engineers。  
- 哪些岗位逻辑被削弱：  
  - 单纯以功能部门边界定义工作；  
  - 靠 title 大而全但责任不清的“AI 负责人”；  
  - 只讲实施、但不讲验证和持续运营。  
- 哪些岗位逻辑被增强：  
  - 端到端 workflow ownership；  
  - 验证、评估、风险与交付证据；  
  - 跨业务、跨技术、跨治理的复合能力。  
- 员工影响：  
  - 一部分通用协调职责可能被吸收到更高颗粒度的 role flow；  
  - 一部分高判断、高验证、高行业语境角色会继续专业化并产生溢价。  
- 争议和阻碍：  
  - 新角色如果只在一两个项目里出现，过早做成长期序列会造成冗余；  
  - 如果 role flow 很稳定但 pay logic 不变，关键人才会很快要求 market premium。  
- 可借鉴点：  
  - 先把新角色定义为 `责任边界 + 可交付物 + 验证方式 + 成功指标`。  
  - 在出现稳定重复需求前，优先用 skill tag / project role / allowance 承接。  
- 不可照搬点：  
  - 模型公司和咨询/交付公司中的角色包，并不等同于普通企业内部需要一比一照搬。  

## 5. Context层：暂不形成结论，但提示我们关注……

- 暂不形成结论，但提示我们关注：**未来很多业务要求“新建序列”，真实诉求可能只是想为稀缺技能争取 pay band 空间**。  
- 暂不形成结论，但提示我们关注：**Leader / Worker / Verifier 这样的 role flow，进入企业内部后未必以岗位形式出现，也可能先以项目角色或 capability badge 出现**。  
- 暂不形成结论，但提示我们关注：**industry embedding 越深，越可能在“端到端变宽”和“关键节点更专”之间同时发生双向运动**。

## 7. 对我们行动的启发

1. 新建岗位/族群/序列前，先问四个问题：是否长期存在、是否跨团队可迁移、是否可稳定评价、是否需要独立 pay logic。  
2. 若只是短期稀缺能力或项目型责任，优先用 `skills tag / market premium / project bonus / temporary allowance`。  
3. 若角色包已稳定出现且承担关键责任链，再考虑新建族群/序列。  
4. 将 job architecture 与 pay architecture 一起设计，不要先造 title 再补薪酬。  
5. 对 `verifier / technical architect / workflow owner` 这类角色，必须同时写清成功指标和不得越界的权限边界。
